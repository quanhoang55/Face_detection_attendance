# Face Recognition Attendance System

## 1. Goal

Build a small attendance application with two frontend tabs:

1. **Employee Enrollment** — upload an employee photo, generate a face encoding, and save the employee in a CSV-backed fake repository.
2. **Attendance Camera** — show the browser camera, recognize enrolled employees, and automatically tick `is_arrive` in the employee list shown below the video.

This is a good design for a local prototype. The browser handles the user interface and camera preview, while the Python backend owns face encoding, recognition, and CSV persistence.

The first version does not require a separate face-tracking model. The backend can use `face_recognition` to detect and recognize faces in selected camera frames. Processing every few hundred milliseconds, instead of every video frame, is sufficient for the prototype. A tracker can be added later if performance requires it.

---

## 2. Main User Flow

### Tab 1: Employee Enrollment

1. The user selects or drops an image such as `alice-nguyen.jpg`.
2. The frontend previews the image and derives `alice-nguyen` as the default employee name.
3. The user may edit the name before saving.
4. The frontend sends the image and employee name to the backend.
5. The backend:
   - validates the file type and size;
   - loads the image with `face_recognition.load_image_file()`;
   - checks that the image contains exactly one face;
   - creates a 128-value face encoding with `face_recognition.face_encodings()`;
   - assigns a stable `employee_id`;
   - writes the employee and encoding to the CSV repository.
6. The frontend shows a success or validation message.

The filename is only a convenient default label. Recognition does not discover a person's real name from their face. It finds the closest stored encoding, and the application returns the name associated with that stored encoding.

### Tab 2: Attendance Camera

1. The user grants camera permission.
2. The frontend displays the live camera using `navigator.mediaDevices.getUserMedia()`.
3. At a controlled interval, for example every 500–1000 ms, the frontend captures a video frame and sends it to the backend.
4. The backend detects all faces in the frame and creates an encoding for each face.
5. Each face encoding is compared with the enrolled encodings using `face_recognition.face_distance()`.
6. If the nearest face is within the configured tolerance, the backend marks that employee as arrived.
7. The backend returns the recognition results and updated employee list.
8. The frontend draws a box and name for recognized faces and ticks `is_arrive` in the list below the camera.

An unmatched face is displayed as `Unknown` and does not update attendance.

## 3. Suggested Architecture

```text
Browser frontend
  ├── Enrollment tab
  │     └── image + employee name
  └── Attendance tab
        └── periodic camera frames
                  │
                  ▼
Python API backend
  ├── enrollment service
  ├── recognition service
  ├── attendance service
  └── CSV repositories
          ├── employees.csv
          └── attendance.csv
```

### Frontend

A simple React or plain HTML/JavaScript frontend is enough. React is useful if the employee list and camera state will grow more interactive.

Responsibilities:

- render the two tabs;
- preview uploaded images;
- request browser camera access;
- capture resized JPEG frames from the video;
- call the backend API;
- display face boxes, names, errors, and attendance state;
- poll or refresh the employee list after recognition.

The frontend must not generate or compare face encodings. Keeping recognition in the backend gives one consistent implementation and avoids sending the known encoding database to the browser.

### Backend

Use Python with FastAPI, `face_recognition`, NumPy, and Pillow or OpenCV.

Responsibilities:

- validate uploads;
- generate and compare face encodings;
- read and write CSV files through repository classes;
- apply the recognition tolerance;
- update attendance only after a verified match;
- return JSON responses to the frontend.

FastAPI and an ASGI server should be added to the backend dependencies because the current project dependencies contain the recognition libraries but no HTTP framework.

## 4. Fake CSV Repository

CSV is acceptable for this prototype, but all file access should go through repository classes so it can later be replaced with SQLite or another database without changing the recognition and API layers.

### `data/employees.csv`

```csv
employee_id,name,image_filename,face_encoding,created_at
emp_001,Alice Nguyen,alice-nguyen.jpg,"[0.0123,-0.0831,...]",2026-10-02T09:00:00+07:00
```

Fields:

- `employee_id`: stable unique identifier generated by the backend;
- `name`: label returned after a successful recognition;
- `image_filename`: original uploaded filename for reference;
- `face_encoding`: JSON text containing the 128 floating-point values;
- `created_at`: enrollment timestamp.

### `data/attendance.csv`

```csv
attendance_date,employee_id,is_arrive,arrived_at,last_distance
2026-10-02,emp_001,true,2026-10-02T09:15:20+07:00,0.4127
```

Fields:

- `attendance_date`: local attendance date;
- `employee_id`: references an employee;
- `is_arrive`: `true` after the first verified recognition that day;
- `arrived_at`: timestamp of the first verified recognition;
- `last_distance`: face distance for debugging and threshold tuning.

Attendance should be stored separately from employees because `is_arrive` changes each day. For an employee with no row on the current date, the API returns `is_arrive: false`.

### Repository interfaces

```python
class EmployeeRepository:
    def list_all(self): ...
    def get_by_id(self, employee_id): ...
    def create(self, employee): ...
    def name_exists(self, name): ...


class AttendanceRepository:
    def list_for_date(self, attendance_date): ...
    def mark_arrived(self, employee_id, arrived_at, distance): ...
```

CSV writes should use a lock and an atomic replace operation to reduce the risk of concurrent requests corrupting the file. This remains a development-only repository; use SQLite or a proper database when multiple backend processes or machines are involved.

## 5. Backend API

### `POST /api/employees`

Enroll an employee using `multipart/form-data`.

Request fields:

- `name`: employee display name;
- `image`: `.jpg`, `.jpeg`, or `.png` file.

Success response:

```json
{
  "employee_id": "emp_001",
  "name": "Alice Nguyen",
  "image_filename": "alice-nguyen.jpg"
}
```

Possible validation errors:

- unsupported or oversized image;
- no face found;
- more than one face found;
- duplicate employee name;
- unreadable image.

### `GET /api/employees`

Return employees combined with today's attendance state.

```json
[
  {
    "employee_id": "emp_001",
    "name": "Alice Nguyen",
    "is_arrive": true,
    "arrived_at": "2026-10-02T09:15:20+07:00"
  }
]
```

The API must never return face encodings to the frontend.

### `POST /api/recognize`

Accept one camera frame as an uploaded JPEG image.

Example response:

```json
{
  "faces": [
    {
      "employee_id": "emp_001",
      "name": "Alice Nguyen",
      "distance": 0.4127,
      "location": {"top": 42, "right": 218, "bottom": 196, "left": 65}
    }
  ],
  "attendance_updated": ["emp_001"]
}
```

For an unmatched face, `employee_id` is `null`, `name` is `Unknown`, and no attendance row is changed.

### `GET /api/attendance?date=2026-10-02`

Return the employee list and attendance state for a selected date. The date can default to today in the configured application timezone.

## 6. Recognition Logic

On backend startup, load employee rows and parse their encodings into NumPy arrays. Reload the in-memory list after a successful enrollment.

For each submitted camera frame:

1. Decode the image and convert it to RGB.
2. Resize it before detection if necessary for better performance.
3. Find faces with `face_recognition.face_locations()`.
4. Generate encodings with `face_recognition.face_encodings()`.
5. Calculate distances with `face_recognition.face_distance(known_encodings, candidate)`.
6. Select the smallest distance.
7. Accept the identity only when the smallest distance is at or below the configured tolerance.
8. Mark the matched employee as arrived if not already marked for the current day.

Start with a tolerance of `0.5` or `0.55` and test it with real employee photos. A smaller value is stricter; the library's common default of `0.6` can produce more false matches in an attendance system.

To reduce accidental attendance updates, the prototype may require the same employee to be recognized in two or three recent frames before marking arrival. This is recommended even though a single-frame match is simpler.

## 9. Rules and Edge Cases

- Enrollment images must contain exactly one clear, front-facing face.
- Reject duplicate employees instead of silently overwriting records.
- A camera frame may contain zero, one, or several faces.
- Mark every recognized employee in a multi-face frame, not just the first face.
- Do not mark `Unknown` faces as arrived.
- Preserve the first `arrived_at` time for the day; repeated matches must not overwrite it.
- Apply a short recognition cooldown to avoid unnecessary CSV writes.
- Use the Asia/Ho_Chi_Minh timezone consistently for daily attendance.
- Limit upload size and validate decoded image content, not only the filename extension.
- Do not expose face encodings in API responses or application logs.
- Show a notice and obtain consent before collecting biometric face data.
- This system recognizes similarity; it does not provide liveness detection. A photo displayed to the camera may fool it.

## 10. Prototype Acceptance Criteria

The first version is complete when:

1. A user can enroll an employee from a JPG or PNG containing exactly one face.
2. The generated 128-value encoding survives an application restart through CSV storage.
3. The camera tab displays a live browser camera feed.
4. A recognized employee is automatically marked `is_arrive: true` for the current date.
5. The list below the camera updates without a manual page refresh.
6. Unknown faces do not change attendance.
7. Multiple employees can be enrolled and distinguished.
8. Invalid files and images with zero or multiple faces produce clear errors.

## 11. Recommended Build Order

1. Implement the two CSV repositories and tests.
2. Implement enrollment and verify that encodings can be saved and reloaded.
3. Implement single-image recognition through the API.
4. Build the enrollment tab.
5. Build camera capture and periodic frame submission.
6. Add the employee attendance list and automatic refresh.
7. Tune tolerance and multi-frame confirmation using real test images.
8. Add security, liveness detection, and a real database only after the core workflow is reliable.
